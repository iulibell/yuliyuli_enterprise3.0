# YuliYuli 面试问答

## 1. 这个项目是做什么的？

这是一个基于 `Spring Boot + Vue3` 的前后端分离视频平台，核心功能包括：

- 视频投稿
- 视频播放
- 视频点赞 / 收藏 / 评论
- 用户关注 / 取关
- 视频搜索与热门推荐

项目重点不只是功能实现，还包括缓存、异步削峰、搜索、工程重构等方面的实践。

## 2. 你在项目里主要负责什么？

我主要负责后端核心链路设计与优化，同时也做了一部分前端交互优化。重点包括：

- 视频列表缓存与并发控制
- 播放、点赞、关注等异步链路
- Redis / RabbitMQ / Elasticsearch 的接入与联动
- 后端代码结构重构和可维护性优化
- 前端搜索建议的防抖与请求取消

## 3. 为什么这个项目要用 Redis？

Redis 主要解决两个问题：

- **缓存热点数据**：比如视频列表、热门推荐，减少数据库读取压力
- **承接异步链路中的中间状态**：比如播放计数、点赞状态、关注集合等

我在项目里还用了 `Redisson` 做分布式锁，避免缓存击穿和并发下重复处理。

## 4. 为什么要用 RabbitMQ？

RabbitMQ 主要用于把高频写操作异步化，避免请求线程直接同步打数据库。

例如：

- 播放
- 点赞
- 评论
- 收藏
- 关注
- 删除视频

这些场景如果都同步写库，在并发稍高时会明显拖慢接口响应。  
所以项目里采用“请求入队 -> consumer 消费 -> 延时任务落库”的方式，达到削峰填谷的效果。

## 5. 为什么还要用 Elasticsearch？

因为视频搜索场景更适合 ES，而不是直接用 MySQL `like`。

原因有三个：

- 检索体验更好
- 扩展性更强
- 更适合后续做热度、相关性等搜索能力

在项目里，ES 主要承接视频搜索和热门视频相关的检索能力。

## 6. 视频播放量是怎么统计的？

项目早期是每次播放都直接写数据库和 ES，这样写放大会很严重。  
后面我做了优化：

1. 播放请求先进入 MQ
2. consumer 只负责把播放量增量累加到 Redis
3. 定时任务批量读取增量
4. 再统一落库并同步 ES

这样做的好处是：

- 降低数据库写压力
- 降低 ES 更新频率
- 更适合高频播放场景

## 7. 你做过哪些性能优化？

比较核心的有这些：

- 修复视频列表缓存锁逻辑，减少并发回源数据库
- 把 Redis `KEYS` 改为 `SCAN`
- 播放统计改为 Redis 累加 + 定时批量落库 / 同步 ES
- 搜索建议增加防抖和请求取消
- 降低高频日志级别，避免日志放大

## 8. 你做过哪些代码结构优化？

我做过几轮比较系统的重构：

- 把鉴权边界统一，明确当前登录校验由 `LoginInterceptor` 负责
- 删除空壳 `JwtTokenFilter`
- 把原来一个很大的延时任务类拆成多个调度类
- 把任务处理逻辑再拆成多个 support 类
- 把 `VideoServiceImpl` 的消息发布和查询逻辑分别抽到独立组件
- 把部分 `Map<String, Object>` 消息体改成强类型 DTO
- 抽取 consumer 公共重试模板
- 引入 `ServiceResult` 统一 service 返回风格

## 9. 为什么要把 `Map<String, Object>` 改成 DTO？

因为 `Map<String, Object>` 有几个明显问题：

- 没有类型约束
- 字段名写错只能运行时发现
- 重构不安全
- 可读性差

改成 DTO 之后：

- 字段含义清晰
- 编译期能发现问题
- consumer / task / service 之间的链路更清楚

比如我在关注链路和视频删除链路里，把消息体改成了 `FollowCommand` 和 `VideoDeleteCommand`。

## 10. 为什么要引入 `ServiceResult`？

之前 service 层很多方法直接返回字符串，比如：

- `"关注成功"`
- `"取消关注成功"`
- `"请完成登录"`
- `"删除失败"`

这样 controller 只能通过字符串判断逻辑，比较脆弱。  

我引入 `ServiceResult` 后，service 至少统一成：

- `success`
- `message`

这样 controller 只看 `isSuccess()` 和 `message`，接口契约会更稳定，也更容易继续扩展成带错误码或 data 的结果对象。

## 11. 你为什么要拆 `DelayedTaskProcessor`？

因为它原来是一个典型的大类，里面同时处理：

- 点赞
- 播放
- 热门播放
- 删除视频
- 关注同步

这会带来两个问题：

- 改一条链路容易影响其他链路
- 读代码时很难快速定位问题

所以我把它拆成：

- `LikeDelayTask`
- `PlayDelayTask`
- `DeleteDelayTask`
- `FollowDelayTask`

并且进一步拆出对应的 support 类，让“调度”和“业务处理”分开。

## 12. 为什么要拆 `VideoServiceImpl`？

因为它之前同时承担了太多职责：

- 查询视频列表
- 发 MQ
- 处理缓存和分布式锁
- 处理热门推荐

这会导致类越来越大，边界不清晰。  

我把它拆成了两个支撑组件：

- `VideoEventPublisher`：专门发消息
- `VideoQuerySupport`：专门处理查询、缓存、热门推荐

这样 `VideoServiceImpl` 更像“业务入口编排层”。

## 13. consumer 层你做了什么优化？

我发现多个 consumer 都在重复写：

- 取重试次数
- `basicNack`
- `basicReject`
- 死信 ack

所以我抽了 `ConsumerRetrySupport`，统一重试逻辑。  
这样做的好处是：

- 避免复制粘贴
- 避免日志文案错乱
- 后续改重试策略更方便

## 14. 这个项目你觉得还有哪些不足？

我会比较坦诚地说：

- 还有部分接口/模块没有完全统一到同一种风格
- 部分 controller 仍然有 `Map` 返回，后续可以继续 DTO 化
- 还没有做系统性的自动化测试
- 还没有真正做压测和线上级监控

但我已经针对最核心的后端链路做了较系统的结构优化，所以这个项目现在已经具备比较清晰的工程骨架。

## 15. 如果继续优化，你下一步会做什么？

我会优先考虑这几件事：

1. 进一步统一 controller / service / DTO 返回风格
2. 给核心链路补集成测试
3. 完善接口文档和部署说明
4. 继续收敛前端重复逻辑
5. 在有时间的情况下做压测和监控补充

## 16. 这个项目最大的收获是什么？

我最大的收获不是“把功能做出来”，而是学会了：

- 怎么把中间件真正用到业务里
- 怎么从“能跑”往“能维护”去重构
- 怎么识别代码里职责过重、边界不清晰的问题
- 怎么逐步把项目整理成更像工程项目的结构
